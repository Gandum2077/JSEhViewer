# 数据库启动失败恢复与诊断

> 状态：恢复入口和脱敏诊断已实现；正式数据库仍为 v1，本文不代表已经启用 v2 迁移。

## 什么时候会看到恢复页

应用现在先执行一个很小的 `bootstrap` 启动壳，再加载原有 `index`。如果数据库备份、版本识别、schema 初始化或模块启动在同步阶段抛出异常，启动壳不会继续进入正常页面，而是显示“数据库恢复”页。

恢复页不会猜测哪份数据库是正确的，也不会自动把备份覆盖回当前数据库。它只做三件事：

1. 停止继续进入会写业务数据的正常页面；
2. 显示只读检查结论和普通用户可执行的恢复说明；
3. 允许用户导出脱敏诊断，以及在明确警告后导出数据库原件或一次性升级前备份。

如果恢复页自身也无法加载，应用只显示最小错误提示，并要求用户保留脚本数据、等待修复版本。

## 普通用户应该怎么做

1. 不要卸载 JSEhViewer、清除 JSBox 脚本数据或手工替换数据库；
2. 点击“导出脱敏诊断 JSON”，把该 JSON 提供给项目维护者；
3. 如果存在“升级前数据库备份”，优先把它导出到只有自己能访问的位置；否则先导出当前数据库原件；
4. 等待或安装修复版本，然后点击“重新启动 JSEhViewer”；
5. 不要把数据库原件上传到公开 Issue、聊天群或公共网盘链接。

数据库原件可能仍包含 E-Hentai Cookie、AI/API Key、WebDAV 密码和用户业务数据。恢复页会在分享数据库文件前再次警告；这类文件不是脱敏诊断。

## 脱敏诊断包含什么

诊断 JSON 只包含：

- App 版本、生成时间和错误类别；
- 错误消息的脱敏、截断版本，不包含 stack；
- 当前数据库、journal/WAL/SHM、升级前备份和未完成临时备份是否存在；
- `user_version`、非系统表数量、已知表白名单中存在的名称、未知表数量；
- `quick_check` 结论和外键违规数量；
- 是否执行过自动恢复。当前实现固定为 `false`。

诊断不会查询 `config` 值、图库、搜索词、上传者、标签或其他业务行。错误文本还会删除 URL query、Bearer token、Cookie/API Key/password 等命名字段和长 token 形状字符串。

## 备份与覆盖规则

- 一次性升级前备份路径是 `assets/database.pre-sync-v1.backup.db`；
- 备份通过同目录临时文件完成后再改名；
- 已存在的升级前备份永不覆盖；
- 恢复页不会删除、移动、改名或覆盖当前数据库和备份；
- 自动恢复刻意不实现，因为在无法确认失败阶段时自动覆盖可能丢失较新的本机数据。

## 自动与真机检查

Node fixture 使用临时目录验证：错误分类、secret 脱敏、schema 元数据、备份保留和零自动恢复。运行：

```sh
npm run test:database-recovery
```

JSBox 开发诊断页的“检查启动失败恢复与诊断脱敏”使用 `assets/cloud-sync-phase1-recovery-diagnostic.*` 隔离临时库，写入专用的 Cookie/API Key/password 哨兵后确认它们不会出现在诊断中，且当前临时库和临时备份保持原样，随后删除所有临时文件。

该真机检查不会故意破坏正式 `assets/database.db`，所以它验证的是恢复诊断的安全边界，而不是人为制造一次真实启动失败。真实恢复页入口另由 TypeScript、Node fixture 和生产 bundle 构建共同覆盖。
